## 1. Reconcile the existing migration history

The read-only audit on 5 October 2026 found that Supabase has the base tables and enquiry hardening already present, but `supabase_migrations.schema_migrations` is absent. The deployed catalog matched the local base and hardening migrations. Recheck before changing anything because this is a production database.

1. Open the Supabase dashboard and verify the project reference is `otqzhocismdjbvvsjnpe`.
2. Run [`audit_remote_schema.sql`](audit_remote_schema.sql) in SQL Editor. It reads schema metadata only. Stop if any base object differs, any workflow name is already occupied, or the project reference is wrong.
3. In a terminal opened in the repository, sign in/link the Supabase CLI to this exact project if needed. Do not put credentials in a command or file.
4. Run `supabase migration list --linked`. Confirm that no remote migration versions are recorded. If anything is listed, stop and reconcile each version against the dashboard audit.
5. Only after the complete catalog comparison confirms equivalence, repair the migration history for the two schema changes that already exist:

   ```sh
   supabase migration repair --linked --status applied 20260906110000 20261004120000
   ```

   This step writes migration-history metadata; it does not run either migration's SQL. Confirm the result with `supabase migration list --linked`; both versions must appear as applied remotely. The official Supabase CLI docs describe `migration repair` as a history-table repair, not as an SQL apply/revert operation: [Database migrations](https://supabase.com/docs/guides/deployment/database-migrations) and [CLI reference](https://supabase.com/docs/reference/cli/supabase-migration-repair).

## 3. Activate customer enquiries and email

1. Attach the actual company domain to Vercel, then configure the same HTTPS site origin in Supabase Auth and the `ALLOWED_ORIGINS` Edge Function secret.
2. Generate a random secret of at least 32 characters and set it as the `ENQUIRY_RATE_LIMIT_SECRET` Supabase Function Secret. The handler uses it to HMAC the platform-provided `cf-connecting-ip`; raw IPs are never stored, and the fingerprints plus random idempotency-key reservations expire after one day. The limiter allows ten new submissions per address in a one-hour window. Repeated or concurrent deliveries of the same idempotency key consume only one slot, including while the first database insert is still in flight. The function fails closed if the secret, edge address or limiter migration is unavailable. Supabase's log-field reference identifies `cf_connecting_ip` as the requester's IP: [Log sources and fields](https://supabase.com/docs/guides/observability/log-field-reference).
3. Deploy the reviewed `submit-enquiry` function to the pinned Form & Frame project. Its browser request saves only through the private server-side function; the anon key does not grant direct customer-table writes.
4. Before accepting enquiries, enable `pg_cron` in Supabase Database → Extensions and run [`schedule_enquiry_rate_limit_cleanup.sql`](schedule_enquiry_rate_limit_cleanup.sql) once as the database owner/admin. pg_cron runs each job with the privileges of the role that created it ([pg_cron job security](https://github.com/citusdata/pg_cron#managing-and-creating-jobs)); the cleaner is deliberately unavailable to browser roles. It schedules deletion of expired HMAC fingerprints and random request keys every minute, even when no requests arrive. Then run the read-only [`audit_public_enquiry_retention.sql`](audit_public_enquiry_retention.sql): `matches_expected_cleanup` must be true, recent job runs should be `succeeded`, neither public role should read the limiter tables or execute its functions, and `empty_search_path` must be true. Re-run the schedule file only if the existing job still has its expected command; it stops on a conflicting job.
5. If email alerts are wanted, verify the business sending domain with the chosen mail provider, then set `RESEND_API_KEY`, `NOTIFICATION_EMAIL` and `NOTIFICATION_FROM` in Supabase Function Secrets. Enquiry emails use one stable event idempotency key across first send and retries, preventing duplicate sends during Resend's 24-hour key-retention window ([Resend idempotency keys](https://resend.com/changelog/idempotency-keys)). Configure a matching privacy notice on the website before accepting customer traffic.
6. Use fictional details from the approved domain for the first test. Verify the saved reference, sequential and concurrent retry idempotency, origin rejection, rate-limit response and recorded email outcome. The privacy notice must describe the one-day retention of pseudonymous abuse-prevention fingerprints and random retry keys. Do not use a real customer until the site has the approved privacy notice and abuse controls.

## 4. Create owner access and phone push

1. Create Anthony's Supabase Auth user using his real company email. Add that exact Auth UUID to `public.profiles` with role `owner`; do not create a shared login for the two-person team.
   The staff client requests sign-in with `shouldCreateUser: false` and verifies the user/profile before loading business records. An Auth user without an owner/staff profile sees an access explanation, not an empty live desk. Disable public sign-ups in the project's Auth settings when explicitly authorized; the client option alone does not change server-wide sign-up policy. After provisioning both identities, test unassigned-account rejection, staff/owner access, session expiry and removal of a staff profile against the live project.
2. Generate one VAPID key pair. Add only its public key to Vercel as `FF_OPERATIONS_VAPID_PUBLIC_KEY`. Store `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, a real `VAPID_SUBJECT` contact and a fresh random `PUSH_DISPATCH_TOKEN` in Supabase Function Secrets. Configure the same dispatch token for `submit-enquiry` and `push-new-enquiry`.
3. Deploy `submit-enquiry`, `push-new-enquiry` and `retry-notifications` after the app and schema are reviewed. The dispatch token protects the function-to-function call; a separate retry token protects the scheduled worker; the service-role key stays on the Supabase server. New enquiries alert all opted-in staff. Quote, build, appointment, invoice and recorded-payment changes alert the other opted-in staff member, omit customer and amount details, and open the relevant mobile app section.
4. For automatic recovery when a provider is temporarily unavailable, enable `pg_net` from Supabase Database → Extensions (`pg_cron` is already required for privacy cleanup). Save one random token of at least 32 characters as `NOTIFICATION_RETRY_TOKEN` in Edge Function Secrets and as `form_frame_notification_retry_token` in Supabase Vault. Then run [`schedule_notification_retries.sql`](schedule_notification_retries.sql) once in that project's SQL Editor. The SQL reads the secret from Vault, so the token itself is never saved in the repository or scheduled command. Confirm the job appears in `cron.job`, inspect recent `net._http_response` results for HTTP 200, and confirm a fictional failed event becomes `sent` after a retry. The worker scans at most 10 due events each minute and uses increasing backoff capped at 16 minutes ([Supabase scheduling guide](https://supabase.com/docs/guides/functions/schedule-functions), [pg_net guide](https://supabase.com/docs/guides/database/extensions/pg_net)).
5. Publish the staff app on the company's HTTPS domain, configure Supabase Auth redirect/site URLs for `/operations/`, then have Anthony sign in on his own phone and press **Enable push alerts**. Permission is requested only after that tap. On iPhone/iPad he must open the site in Safari, choose **Share → Add to Home Screen**, launch that icon and use iOS/iPadOS 16.4 or later.
6. Submit a fictional enquiry from the allowlisted website origin. Confirm that the enquiry appears in Work, a push alert arrives on Anthony's phone, tapping it opens that enquiry, and `notification_events` records delivery. Test a transient failure on one of two registered staff devices and confirm the event stays retryable while the notification tag prevents alerts from stacking on a device that already received it. Then have one staff member send a quote, change a build, book a visit, send an invoice and record a fictional payment. Verify each relevant alert goes to the teammate who did not make the change, opens Work, Calendar or Money as appropriate, contains no customer/amount details, and records delivery. Confirm that saving the enquiry still succeeds if push is unavailable.

## Remaining business decisions

The software must not invent the business domain/email, legal seller name and billing address, privacy/data-retention terms, VAT registration/treatment, invoice sequence and payment terms, cancellation policy or accounting provider. Stripe is not connected. The app can record manually received payments and print/save a configured invoice as PDF; invoice email delivery, live Stripe checkout/webhook, private customer-photo upload and an optional bot challenge for higher-volume traffic require their own reviewed implementation and test.
