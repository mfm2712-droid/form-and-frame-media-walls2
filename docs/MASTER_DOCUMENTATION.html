1. About this document

This is the handover master document for the Form & Frame website and Operations app. It was written on 16 October 2026 against production commit 5354a28 (site) and is kept in the repository at docs/MASTER_DOCUMENTATION.html.

How to read the labels. Real screenshot = captured from a build of the repository files (the same files production serves), rendered in a real browser. Design prototype – not the live app = a concept page in the repository that is explicitly labelled fictional and not connected to data. Verified live = exercised on the production site. Verified by tests only = covered by automated tests with fictional data but not exercised live. Not verified / Blocked = could not be checked; the reason is stated.

Important limit: no staff sign-in was available during this review, so the signed-in Operations screens (Owner Desk, pipeline, calendar, quotes, invoices) were not captured or exercised live. Section 9 describes them from the source code and the tests, and section 10 shows the redesigned enquiry workspace using a simulated backend; both say so on every item.

10.8 Mobile

On a phone the workspace fills the screen with a back button, a swipeable progress tracker, one large primary action, and single-column cards. Buttons are at least 44 px high (checked).

10.9 Safeguards

  • Two phones opening the same new enquiry cannot overwrite a later status: the save only applies while the enquiry is still New.
  • If a save fails, the screen reverts and says so.
  • While you are typing in a form, background refreshes wait until you finish.
  • A completed survey is no longer dropped from the data load, so a required site assessment no longer blocks quotes after the visit is done.
  • Updating a quotation, job or invoice uses the existing database rules (status order, locking, overpayment), which still apply.

10b. Push notifications and the notification centre (new)

Honest status. Everything below is built, deployed with the app and checked by 177 automated tests and a 34-check browser run on a simulated backend (including an emulated iPhone, an installed iPhone app and Android). No alert has yet been delivered to a real phone. That needs the one-off setup in 10b.6, which only Mark can do, and a physical device. Real-device delivery is Not verified.

10b.1 What happens, end to end

  1. A customer submits the website form. The submit-enquiry function saves it and immediately asks push-new-enquiry to alert every owner/staff device. This already existed and is unchanged.
  2. The alert reaches each device through the browser's push service, even when Operations is closed. It says only: New Form & Frame enquiry. Enquiry FF-… is ready to review.
  3. Tapping it opens /operations/?enquiry=<id>: that customer's command centre, with the next step “Open” or “Create quotation” highlighted. If Operations is already open it navigates there instead of opening a second window.
  4. If a push is missed or fails, the existing outbox and retry-notifications worker try again with back-off (status kept in notification_events).
  5. Quotation, acceptance, appointment, job, invoice and payment changes use the same outbox. A database trigger queues them; the retry worker delivers them to the other owner (the person who made the change is not alerted about their own action). Taps open the same project.

Duplicate control: the same alert raised twice within 30 seconds is stored once; each alert has a fixed tag so a retry replaces rather than stacks; the person who acted is excluded; an owner who switched a category off is skipped by the push function on the server.

10b.3 Notification centre

The bell in the header shows the unread count (and the app icon badge and browser tab title where supported). It lists the push events from the existing notification_events outbox, newest first, with relative timestamps and a “Opens project” hint. Mark read clears one; Mark all read clears everything; opening a project clears that project's alerts. Read state is stored per person in notification_reads, so Anthony reading something does not clear it for Mark.

10b.4 Preferences and this device

Settings & install shows whether this phone is receiving alerts (On / Off / Blocked / needs installing), an Enable notifications button, a Send test notification button once enabled, and six switches. Switches are per person and saved in notification_preferences; a missing row means everything is on.

10b.9 Android status-bar icon (white square investigation)

Symptom. On a Samsung phone the expanded notification showed the green-and-gold logo, but the tiny top-bar icon was a solid white square.

What was checked. The deployed FF badge is a 96×96 RGBA PNG, about 62% fully transparent, every visible pixel pure white, corners clear, nothing touching the edge. Treated the way Android treats a badge (alpha only, tinted white), it renders as a clear “FF”, so the image itself was not the cause. It is the same kind of file as the working reference app's badge. A real Chromium run confirmed the worker passes that badge and the green-and-gold icon-192.png to showNotification, and both URLs answer HTTP 200.

Most likely causes found, and what changed.

  • The worker could be stuck waiting. Our worker had no skipWaiting/clients.claim. In real Chromium, a changed worker stayed in waiting while the app window was open, so the phone kept running the old worker (and its old icon) until every window closed. The reference app takes over immediately. Now fixed: the worker activates at once and the app registers one stable worker URL.
  • An installed app (WebAPK) carries its own status-bar icon. Chrome documents the small icon for installed apps as coming from the app's packaged icon, which is fixed when the app is installed or updated, and some reports say the badge option is ignored there. Our manifest had no monochrome icon until today, and the combined “any maskable” opaque icon is what Android could have flattened into a square. Now fixed: monochrome 96 and 192 px FF icons are declared, and the opaque icons are declared separately as “any” and “maskable”. Sources: Chromium change 2362423002, blink-dev icon purposes, and an open-source report of the same symptom kinkord #154.

Still needs the actual phone. Android refreshes an installed app's packaged icon on its own schedule (days) and only when it re-reads the manifest. To force it: remove Form & Frame from the home screen, open the site in Chrome, install it again, enable notifications, then use Send test notification. Settings, Status-bar icon shows the worker version and the FF preview. If a square remains after a clean reinstall, the next step is a Trusted Web Activity package, where the small icon is a native Android resource the developer controls (not done; not needed unless the clean reinstall fails).
